## 3. 统一执行规则

### 3.1 每个最小交付的固定循环

- [ ] 读取该问题涉及的代码、现有测试和接口文档。
- [ ] 用测试报告中的步骤或新增的自动化测试复现失败，保存失败命令、状态码或断言。
- [ ] 只实现让该失败通过的最小改动。
- [ ] 运行该问题的目标测试；目标测试不通过时禁止提交。
- [ ] 运行 `git diff --check`，确认没有空白符错误。
- [ ] 运行 `git diff --staged`，逐文件确认没有夹带无关修改。
- [ ] 运行暂存区敏感信息检查；发现真实密码、Token、Key 时立即取消暂存。
- [ ] 使用约定的提交信息提交，不使用 `fix all`、`update`、`misc` 等无意义信息。
- [ ] 执行 `git status --short`，确认提交后只剩下一步尚未处理的内容。

### 3.2 最小验证规则

1. 单元逻辑只跑对应测试文件；不因一个函数修改而先跑全部测试。
2. 路由、认证、数据库和上传等跨边界修改，至少执行单元测试加一次对应 HTTP 或浏览器验证。
3. 每完成一个 P0，执行该 P0 的目标测试；四个 P0 全部完成后再执行一次 P0 检查点。
4. 每完成一个 P1，执行对应目标测试；十个 P1 全部完成后再执行一次 P1 检查点。
5. P2 的性能项先测试生产构建；指标达标时只交付证据，不为了“看起来做了优化”而修改代码。
6. 根目录 `npm run lint` 当前带 `--fix`，在 P2-5 修正脚本前不得把它当作只读验证；此前使用：

```powershell
npx eslint . --ext .vue,.js,.ts
```

### 3.3 提交规则

- 一个提交只处理一个可独立回退的逻辑变化。
- 测试和使该测试通过的实现放在同一提交；不提交长期红灯测试。
- 格式化、重构、依赖升级、业务修复不得混在同一提交。
- 单次提交优先控制在 1～5 个文件；超过 5 个文件时必须在提交前重新判断是否可拆分。
- 每次提交前必须确认 `mood_health_server/.env` 仍为 ignored 状态。
- 文档证据在阶段检查点集中提交，避免每个业务提交都修改同一个报告文件。

### Task 8：统一 API 响应契约（P1-3）

**权威契约：** `docs/tech-design/03-api-contract.md`。所有 JSON 响应统一为：

**接口：** 抽出一个认证凭据解析函数，Cookie 与 Bearer 同时存在时继续按现有规则选择 Cookie 作为实际认证 Token；认证中间件把本次已验证 Token 的剩余有效期放入 request 私有字段，不写日志。`POST /logout` 改为必须先 `authenticate`：正常情况下撤销实际使用的 Token；若请求同时携带两个不同 Token，只撤销通过验证且 userId 与当前用户一致的凭据，拒绝借当前 Cookie 撤销其他账号 Token。Redis 只保存 `sha256(token)`，key 为 `auth:revoked:<digest>`，TTL 等于 JWT 剩余有效秒数。日志不得输出原 Token 或摘要。

**验证：** 登录取得 Token → 受保护接口 200 → 退出 200 → 使用同一 Bearer Token 请求返回 401；等待/伪造过期 Token 不产生永久 Redis key。

CLI 支持 `npm --prefix mood_health_server run db:rollback -- --step 1`；默认只回滚最近 1 个已应用迁移，`--step N` 回滚最近 N 个，超过已应用数量时只回滚现有数量。继续使用迁移锁和 checksum 校验。

**验证：** 单元测试先证明当前实现会回滚全部，再验证 1、2、超量和非法 step。随后在隔离 MySQL 中应用 24 个迁移，只回滚 1 个，状态应为 23 applied/1 pending，再重新应用恢复 24 applied。

**提交：** `fix: limit migration rollback to explicit steps (P2-4)`
