# Codex 任务：基于现有代码审计并完成 P0 全链路开发计划

你现在位于本项目代码仓库根目录。

本次任务不是简单按照旧开发计划机械开发，也不是只检查前端或后端。你需要以**当前仓库中的实际代码、数据库结构、接口实现和测试结果为唯一事实依据**，完成以下工作：

1. 从旧开发计划中提取待完成的 P0。
2. 审计当前代码是否已经实现这些 P0 功能。
3. 已经真实完成的功能跳过，不重复开发。
4. 部分完成的功能补齐整条链路。
5. 完全未完成的功能进行全链路开发。
6. 根据代码真实情况重写并生成详细的 `Plan P0 v1.0`。
7. 按更新后的 Plan P0 v1.0 继续完成开发。
8. 只有通过代码检查、测试和验收后，才能将任务标记为完成。

---

## 一、工作原则

### 1. 代码是事实源

旧开发计划可能已经过时，计划表中的“待开发”“已完成”等状态不能直接相信。

你必须通过以下证据判断实际完成情况：

* 前端页面、组件、路由和状态管理
* API 请求封装及调用位置
* 后端 Controller、Router、Service、Repository 等代码
* 数据库表、字段、索引、约束和迁移文件
* 权限控制和用户数据隔离
* 参数校验和异常处理
* 自动化测试
* 可执行的构建、启动和测试结果
* 页面到接口再到数据库的真实调用链路

禁止仅因为存在同名文件、空壳方法、静态页面或 Mock 数据，就判断功能已完成。

### 2. 必须检查整条链路

每个任务都必须至少检查以下链路：

```text
用户入口
→ 前端页面与交互
→ 前端状态管理
→ API 请求封装
→ 后端路由/控制器
→ 业务服务
→ 数据访问层
→ 数据库表与字段
→ 权限及数据隔离
→ 参数校验
→ 异常处理
→ 自动化测试
→ 实际验收
```

不能只修改前端，也不能只补后端接口。

### 3. 不重复开发

如果代码中已经存在满足验收标准的实现：

* 保留现有实现；
* 不重复创建页面、接口、表或字段；
* 在 Plan v1.0 中将其标记为“已完成，跳过开发”；
* 写明代码证据和测试证据。

如果现有实现只完成了一部分，则标记为“部分完成”，只补齐缺失部分。

### 4. 保持现有工程规范

在修改代码前，先识别项目现有的：

* 技术栈；
* 目录结构；
* 命名规范；
* API 返回结构；
* 数据库访问方式；
* 鉴权方式；
* 异常处理方式；
* 测试框架；
* UI 组件体系；
* 日志体系；
* 环境变量管理方式。

新增实现必须尽可能复用现有架构和公共能力，不要无必要地引入第二套技术方案。

### 5. 不允许虚假完成

以下情况不能标记为完成：

* 只有页面，没有真实接口；
* 只有接口，没有前端入口；
* 使用硬编码或 Mock 数据代替数据库查询；
* 数据库字段缺失；
* 普通用户可以访问管理员接口；
* 可以查看其他用户的数据；
* 只有成功路径，没有异常处理；
* 测试无法运行；
* 构建失败；
* 验收标准未验证；
* 功能存在但没有调用入口；
* 代码存在明显 TODO、占位符或未实现方法。

# P0-AI-01 多维情绪上下文分析

## 目标

AI 分析不能只依赖用户本次输入，需要综合：

* 当前情绪类型；
* 当前情绪强度；
* 当前文字描述；
* 用户近期情绪记录；
* 情绪变化趋势；
* 最近一次或近期心理测评结果；
* 必要的历史 AI 分析信息。

## 前端审计与实现要求

检查并补齐：

* AI 分析入口；
* 当前分析所引用的数据范围说明；
* 加载状态；
* 空数据状态；
* 请求失败状态；
* 超时提示；
* 重试操作；
* 结构化分析结果展示；
* 不得展示其他用户的数据。

## 后端审计与实现要求

检查并补齐：

* 当前用户身份获取；
* 用户近期情绪记录查询；
* 用户测评结果查询；
* 上下文聚合服务；
* AI Prompt 构建；
* 结构化输出格式；
* AI 输出解析；
* 超时控制；
* 重试策略；
* AI 服务异常兜底；
* 用户数据隔离；
* 合理的查询数量限制，避免无限读取历史记录。

## 数据库审计与实现要求

检查：

* 情绪记录表是否包含情绪类型、强度、描述和时间；
* 测评结果表是否支持查询用户近期结果；
* 是否需要新增 AI 分析记录；
* 是否存在用户 ID 和时间字段索引；
* 是否存在数据关联字段和外键约束。

不要在已有结构能够满足需求时重复建表。

## 验收标准

* 同一用户在不同历史数据下获得差异化分析；
* 不同用户的数据严格隔离；
* 没有历史数据时仍能合理返回；
* 接口异常时页面不崩溃；
* AI 结果不是前端硬编码；
* 分析请求能够追溯到真实用户数据。

## 后端审计与实现要求

检查并补齐：

* 建议生成模板；
* 个性化上下文输入；
* 结构化 JSON 或稳定的数据结构；
* 输出字段校验；
* 安全规则；
* 非诊断内容约束；
* AI 输出异常时的固定安全兜底；
* 建议与情绪记录或分析记录的关联；
* 重复请求和幂等性处理。

## 数据库审计与实现要求

检查是否需要保存：

* 用户 ID；
* 关联情绪记录 ID；
* 关联测评结果；
* AI 分析内容；
* AI 建议内容；
* 生成时间；
* 模型或版本信息；
* 风险等级；
* 生成状态。

## 验收标准

* 建议与当前用户的真实情绪相关；
* 结果包含四段式结构；
* 包含明确的非诊断免责声明；
* 建议包含可以执行的具体行动；
* AI 异常时返回安全兜底；
* 高风险输入不会只返回普通日常建议。

## 后端审计与实现要求

* 当前用户历史列表接口；
* 当前用户历史详情接口；
* 分页参数；
* 排序规则；
* 用户所有权校验；

* 空列表和接口失败时页面行为正常。

# P0-AI-04 AI 安全边界与异常兜底

## 目标

降低不适当心理建议和 AI 服务失败带来的风险。

## 必须具备的安全边界

* 不输出医学诊断结论；
* 不声称替代医生、心理咨询师或专业机构；
* 高风险内容不能按照普通情绪建议处理；
* AI 服务不可用时返回固定安全提示；
* 页面不能因为 AI 输出格式错误而崩溃；
* 日志中不得记录密码、Token 等敏感数据。

## 前端审计与实现要求

检查并补齐：

* 非诊断免责声明；
* 高风险提示；
* 专业帮助提示；
* AI 请求失败提示；
* 超时提示；
* 重试入口；
* 非法响应格式的兼容展示；
* 对危险内容不展示鼓励性或误导性普通建议。

## 后端审计与实现要求

检查并补齐：

* 输入内容风险识别；
* 输出结果安全检查；
* 高风险分级；
* 风险命中规则；
* 固定安全兜底；
* AI 超时；
* AI 网络异常；
* AI 返回空内容；
* AI 返回非法 JSON；
* AI 返回不完整字段；
* 异常日志；
* 统一错误码和错误信息；
* 高风险内容的处理策略。

优先复用项目已有内容检测能力，不要重复构建完全独立的安全模块。

## 数据库审计与实现要求

按项目实际情况判断是否需要：

* 风险等级；
* 命中规则；
* 风险处理状态；
* AI 请求状态；
* 错误类型；
* 创建时间；
* 必要的错误日志记录。

## 验收标准

至少覆盖以下测试场景：

1. 普通情绪输入；
2. 空输入；
3. 超长输入；
4. 高风险输入；
5. AI 超时；
6. AI 返回空内容；
7. AI 返回非法格式；
8. 未登录请求；
9. 访问他人的 AI 记录；
10. 重复提交。

* 数据能够从原始业务表复核；
* 时间范围切换有效；
* 普通用户不能访问；
* 不存在静态模拟数据；
* 同一指标在不同页面上的含义保持一致。

20. 代码中的 TODO、FIXME、Mock 和占位实现。

## 四、为每个任务建立代码证据矩阵

对 8 个 P0 任务分别输出审计矩阵。

格式如下：

| 任务ID | 审计结论 | 前端证据 | 后端证据 | 数据库证据 | 权限证据 | 测试证据 | 缺失项 | 后续动作 |
| ---- | ---- | ---- | ---- | ----- | ---- | ---- | --- | ---- |

审计结论只能使用：

* `已完成`
* `部分完成`
* `未完成`
* `阻塞`

### 已完成的判定要求

只有同时满足以下条件才能判定为已完成：

* 存在真实用户入口；
* 前端调用真实 API；
* 后端存在完整业务逻辑；
* 数据来自真实数据库；
* 权限正确；
* 异常路径已处理；
* 验收标准已满足；
* 相关测试通过；
* 构建成功。

### 部分完成的典型情况

例如：

* 页面存在，但仍使用 Mock 数据；
* 接口存在，但没有前端调用；
* 接口存在，但没有用户隔离；
* 数据库存在，但没有迁移；
* 功能能运行，但没有错误处理；
* 图表存在，但数据口径错误；
* AI 能返回结果，但没有结构化输出；
* 历史列表存在，但详情接口可以越权；
* 有实现但没有测试或无法通过构建。

## 五、生成 Plan P0 v1.0

完成代码审计后，在仓库中创建或更新：

```text
docs/PLAN_P0_V1.0.md
```

如果项目已有规划文档目录，则放入现有文档目录，但文件名应保持清晰。

Plan P0 v1.0 必须以当前代码真实情况为基础，而不是复制旧计划。

### 文档必须包含以下章节

## 1. 项目现状

说明：

* 技术栈；
* 前后端目录；
* 数据库；
* 鉴权机制；
* AI 服务；
* 测试框架；
* 当前构建状态；
* 当前主要风险。

## 2. P0 审计结论摘要

列出：

* 已完成任务；
* 部分完成任务；
* 未完成任务；
* 阻塞任务；
* 从旧计划中删除或合并的重复项；
* 与既有基础功能重叠的任务。

## 3. 范围说明

明确：

* 本轮必须完成的内容；
* 本轮不包含的 P1、P2；
* 因已有代码而跳过的内容；
* 因架构原因需要调整的旧计划内容；
* 不纳入本轮的 `P0-DEMO-*` 项，因为旧表中其实际优先级为 P2。

## 4. 任务拆解

每个未完成或部分完成任务必须拆成可执行子任务。

每个子任务必须包含：

| 字段     | 要求                   |
| ------ | -------------------- |
| 子任务ID  | 例如 `P0-AI-01-BE-01`  |
| 所属任务   | 对应原始 P0              |
| 当前状态   | 已完成、部分完成、未完成或阻塞      |
| 当前代码证据 | 文件路径、类名、方法名、路由或表名    |
| 问题描述   | 当前缺失或错误              |
| 修改范围   | 需要修改的文件和模块           |
| 前端任务   | 页面、组件、状态、API 调用      |
| 后端任务   | 路由、服务、数据访问、校验        |
| 数据库任务  | 表、字段、索引、迁移、约束        |
| 权限任务   | 角色、资源所有权、越权防护        |
| 异常处理   | 空数据、超时、错误码和重试        |
| 测试任务   | 单元、集成、接口、E2E         |
| 验收步骤   | 可复现的操作流程             |
| 完成定义   | 哪些证据齐全后才算完成          |
| 依赖项    | 前置任务或基础模块            |
| 风险     | 数据、兼容性、安全或性能风险       |
| 预计修改文件 | 明确到具体文件路径，无法确定时写候选路径 |
| 实施顺序   | 数字顺序                 |

## 六、实施要求

生成 Plan P0 v1.0 后，不要停止在分析阶段。

继续按照 Plan 实施所有“部分完成”和“未完成”任务。

### 实施规则

1. 按依赖顺序执行；
2. 每次只处理一个清晰的子任务；
3. 修改前阅读相关上下游代码；
4. 优先复用现有公共组件和服务；
5. 数据库修改必须有迁移；
6. 新增接口必须有权限和参数校验；
7. 新增前端功能必须处理加载、空数据、失败和重试；
8. 不允许保留 Mock 数据；
9. 不允许提交无调用入口的孤立代码；
10. 不允许通过删除测试来让测试通过；
11. 不允许降低安全校验；
12. 不允许把敏感数据写入日志；
13. 不要无关地重构整个项目；
14. 保留现有已完成功能；
15. 发现旧计划不合理时，以代码架构为准更新 Plan，并记录调整原因。

* 权限越权测试；

* AI 异常场景测试。

### 核心端到端流程一

```text
普通用户登录
→ 创建情绪记录
→ 完成或读取近期测评
→ 请求 AI 分析
→ AI 聚合当前用户上下文
→ 返回结构化分析和建议
→ 保存 AI 建议历史
→ 在历史列表查看
→ 打开历史详情
```

### 核心端到端流程二

```text
管理员登录
→ 打开管理驾驶舱
→ 切换时间范围
→ 查看 KPI
→ 查看情绪趋势与分布
→ 查看测评分布
→ 查看模块使用统计
→ 与数据库原始数据核对
```

### 权限流程

```text
普通用户访问管理员接口
→ 应被拒绝

用户 A 请求用户 B 的 AI 历史详情
→ 应被拒绝或返回不存在

未登录用户请求受保护接口
→ 应被拒绝
```
