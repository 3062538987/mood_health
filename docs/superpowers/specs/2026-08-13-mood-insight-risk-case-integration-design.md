# 情绪洞察、AI 分析与风险个案整合方案

> 状态：方案已确认，可进入实施计划阶段
>
> 确认日期：2026-08-13
>
> 已确认隐私边界：风险个案详情展示完整聚合图表和结构化 AI 报告，但不展示、传输或复制原始日记正文。

## 1. 目标

本方案解决五个相互关联的问题：

1. “情绪洞察”和“情绪分析”入口、周期选择、AI 文案和趋势内容重复，用户难以理解二者区别。
2. AI 分析报告中的“发现的模式”排版异常，且页面没有足够清晰的证据说明报告是否由真实 AI 生成。
3. 完成一个月分析后，切换到三个月时生成入口消失，页面只显示“分析完成”。
4. 用户实际有大量情绪记录，但三个月、六个月视图只展示了接近一个月的数据。
5. 用户侧情绪趋势和 AI 报告没有进入后台风险个案；现有演示数据又无法触发风险个案，导致管理员无法验收完整链路。

最终产品只保留一个用户入口“情绪洞察”，在同一页面完成数据事实查看、AI 报告生成、周期切换和历史报告回看。后台风险个案复用同一套聚合口径和已落库 AI 报告，为有权限的管理员提供只读视图。

## 2. 当前实现核查结论

### 2.1 两个功能确实重复

当前二级导航同时提供“情绪洞察”和“情绪分析”。两者都包含时间范围切换、情绪概览和 AI 生成内容，并分别调用不同的页面与接口。仓库中还存在一份未被当前路由使用的旧洞察页面，形成多套并行实现。

这不是简单的命名相近，而是产品能力、前端页面和后端调用链重复。继续维护两个入口会导致周期口径、加载状态、错误提示和报告结构进一步分叉。

### 2.2 AI 调用是真实的，但溯源表达有错误

2026-08-13 对当前 MySQL 数据进行了只读核查。最新的 7 天和 1 个月报告均已写入 `mood_analysis_versions`，包含非空摘要、`model=deepseek-chat` 和 `promptVersion=1.0.0`，支持“报告经过真实 AI 服务生成并成功落库”的结论。

但 Python Provider 将 `provider` 固定写成了 `openai`。这表示“使用 OpenAI 兼容协议”，不等于实际供应商是 OpenAI；当前实际模型是 DeepSeek。该字段会误导用户和管理员，必须改为来自受控配置的真实供应商标识，例如 `deepseek`。

系统必须继续坚持失败关闭：只有 AI 返回内容通过合同校验并成功写入数据库，状态才能变为“分析完成”。网络错误、模型错误、JSON 校验失败或落库失败都必须显示明确失败，不得生成本地兜底报告冒充 AI 结果。

### 2.3 “发现的模式”异常来自合同不一致

前端类型把 `patterns[].evidence` 定义为字符串数组，并使用列表循环渲染；Node 与 FastAPI 合同则把该字段定义为单个字符串。当前数据库中的真实报告也保存为字符串。

因此前端可能把一句依据按单个字符循环输出，形成大量异常列表项。这是数据合同错误，不是单纯调整间距或字体即可解决的问题。

统一合同采用：

```ts
interface AnalysisPattern {
  title: string
  observation: string
  evidence: string[] // 1—3 条可验证依据
  caveat?: string
}
```

AI 提示词、FastAPI Pydantic 模型、Node TypeScript 合同、数据库读回类型和 Vue 组件必须同时修改。对已有字符串报告只在读取层兼容为单元素数组，不批量迁移历史记录。

### 2.4 三个月、六个月被错误缩成一个月

用户页面当前把 `3m` 和 `6m` 都转换成了 `month`，导致图表接口实际只查询最近一个月。只读数据库核查显示演示账号当前分别有：7 天 8 条、1 个月 32 条、3 个月 93 条、6 个月 182 条、1 年 365 条。页面在三个月、六个月下仍按一个月取数，所以用户看到的记录明显偏少。

更严重的是，图表使用一个月数据，而 AI 分析调度器按 90 天或 180 天取数，同一页面的“数据事实”和“AI 报告”可能不在同一数据范围内。

### 2.5 生成按钮消失是状态机缺口

当前页面只有在“选中周期不存在任何分析版本”时显示生成按钮。一旦该周期存在 `pending`、`processing`、`completed` 或 `stale` 版本，按钮就被状态条替换；完成态又没有再次生成入口。

周期按钮本身虽然存在，但切换后加载到任何历史版本都会让生成入口消失。页面需要把“周期选择”“报告状态”和“可执行动作”分离，不能用一条互斥条件控制整个操作区。

### 2.6 风险演示数据无法命中当前规则

当前自动风险个案支持三类独立信号：最近连续 7 个自然日每日主情绪平均分低于 5、树洞高风险内容、AI 问答高风险内容。满足任一信号即可自动建案。

现有 `demo_support_admin` 虽有 365 天数据，但最近 7 天全部为快乐且强度为 8；唯一连续 7 天低分区间位于 2026-06-26 至 2026-07-02，已经超出规则的最近 7 天窗口。当前数据库风险个案数量为 0，所以管理员页面无法验证不是操作问题，而是演示数据与实时规则错位。

此外，管理员账号本身不应作为学生风险样本。风险演示必须使用独立的学生账号，风险候选查询也必须限制学生角色。

## 3. 方案比较

### 方案 A：统一“情绪洞察”入口，并向风险个案提供只读聚合视图（推荐并已确认）

保留一条用户链路，以结构化分析能力较完整的现有情绪分析页为基础，合并统计图表、AI 报告、状态与历史。后台风险个案通过受权限保护的接口读取同口径聚合数据和已落库报告。

优点是用户理解成本最低、数据口径唯一、重复代码可清理，后台也不会另造一套风险分析。缺点是需要同时整理路由、周期合同、AI 合同与后台接口，属于跨前后端改造。

### 方案 B：继续保留“洞察”和“分析”，分别定位为统计页与 AI 页

“洞察”只展示图表，“分析”只生成 AI 报告。实现改动相对较小，但用户仍需在两个页面来回切换，两个页面的周期、空状态和数据范围仍容易不一致，后台整合也要决定引用哪一套数据。

### 方案 C：用户侧只保留统计洞察，AI 报告仅在后台生成

能够减少用户侧复杂度，但会取消用户已经在使用的 AI 报告能力，也不能解决用户希望自行查看不同周期报告的需求，不适合作为本项目方案。

综合毕业设计展示完整性、可解释性和后续维护成本，采用方案 A。

## 4. 用户侧统一页面设计

### 4.1 导航与路由

- 二级导航只显示：情绪记录、情绪档案、情绪洞察。
- “情绪洞察”作为唯一产品名称，避免继续同时使用“洞察”“分析报告”描述同一能力。
- 选定一个规范路由作为唯一实现；旧 `/mood/analysis` 或 `/mood/insight` 路由保留重定向，避免首页、历史收藏和旧链接失效。
- 删除或下线未被使用的旧洞察页面和重复 API 包装，但只能在测试确认无引用后执行。

### 4.2 页面结构

页面从上到下固定为：

1. 周期选择：7 天、1 个月、3 个月、6 个月、1 年。
2. 数据范围说明：实际起止日期、纳入的独立情绪记录数、记录天数、数据更新时间。
3. 情绪概览：主要情绪、平均强度、正向/中性/负向比例。
4. 图表：情绪分布、情绪强度趋势、正负情绪占比。
5. AI 报告操作与状态。
6. 结构化 AI 报告：概况、发现的模式、可能相关因素、建议行动、何时寻求帮助、数据限制。
7. 历史报告：默认折叠，按当前周期分页查看。
8. 隐私说明。

所有周期按钮始终可见，不因当前报告状态而消失。切换周期后，图表、数据范围、最新报告和历史列表必须一起刷新。

### 4.3 周期唯一口径

前端、Node 和 FastAPI 统一使用 `7d | 1m | 3m | 6m | 1y`，禁止再将 3 个月、6 个月降级映射为 `month`。

图表和 AI 报告必须共享同一份服务端数据范围解析结果。接口响应至少返回：

```json
{
  "period": "3m",
  "dateRange": { "start": "2026-05-13", "end": "2026-08-13" },
  "recordCount": 93,
  "recordDays": 93,
  "aggregation": "daily"
}
```

长周期不应为了绘图直接丢弃数据。可以按周或月压缩趋势点，但 `recordCount` 必须统计全部记录，并在界面标明图表聚合粒度。AI 输入使用全部记录的服务端聚合结果，不把原始日记或截断后的前 20 条列表当作完整周期数据。

### 4.4 AI 报告状态机

每个周期独立维护状态：

| 状态 | 页面内容 | 可执行动作 |
| --- | --- | --- |
| 无记录 | 空状态及记录入口 | 去记录情绪 |
| 有记录、无报告 | 展示图表和数据范围 | 生成当前周期报告 |
| 等待/处理中 | 保留图表，显示进度 | 禁止重复触发，可切换周期 |
| 已完成 | 展示完整报告 | 刷新、查看历史、重新分析 |
| 数据已变化 | 展示旧报告并标明过期 | 基于最新数据生成新报告 |
| 可重试失败 | 展示明确错误 | 重新分析 |
| 最终失败 | 保留情绪记录和图表 | 稍后重试，不伪造结果 |

“1 个月完成”不得影响“3 个月”的按钮状态。所有读取和生成操作都必须显式携带当前 `period`，异步返回时还要校验返回周期，防止用户快速切换后旧请求覆盖新页面。

同一周期点击“重新分析”时应创建可审计的新版本，而不是因为数据未变化就永远复用旧结果。为了控制调用次数，可增加明确的冷却时间或每日次数限制，但不能让按钮无解释地消失。

### 4.5 AI 真实性与可解释性

用户侧报告头部显示：

- “AI 已生成”状态；
- 报告生成时间；
- 纳入记录数和日期范围；
- 分析批次编号或可复制的报告编号；
- 数据变化后显示“报告基于旧数据”。

供应商、模型、提示词版本、请求编号和数据版本完整保存在数据库与服务日志中。普通用户界面可使用简洁的“AI 已生成”表达，后台个案详情和调试信息中显示真实 `provider/model/promptVersion`，用于验收与追溯。

只有以下条件全部满足才显示“分析完成”：AI 请求成功、返回 JSON 通过严格合同校验、禁止字段检查通过、数据库落库成功、重新读取到非空结构化结果。

## 5. “发现的模式”展示规范

每个模式使用独立卡片，包含：

- 模式标题：一句话概括；
- 观察结果：一至两句自然语言；
- 数据依据：最多三条列表，每条为完整句子；
- 限制说明：样本少、记录不连续或只能说明相关性时显示。

禁止把单个字符串逐字符循环。服务端还需限制模式数量和文本长度，避免 AI 返回过长内容撑坏页面。移动端按单列显示；桌面端也优先保持纵向阅读，不把不同长度的模式强行挤成不等高多列。

## 6. 后台风险个案整合设计

### 6.1 个案详情新增“情绪证据”区域

风险个案详情增加以下只读内容：

1. 风险触发原因：显示规则名称、首次命中时间、最近命中时间和对应统计值。
2. 情绪概览：最近 7 天、30 天、90 天可切换；默认打开触发规则对应周期。
3. 完整聚合图表：记录天数、记录条数、主要情绪、强度趋势、情绪分布和极性占比。
4. 结构化 AI 报告：读取该学生已成功落库且与所选周期匹配的最新报告。
5. 报告溯源：生成时间、报告编号、真实供应商和模型、提示词版本、纳入记录数、数据日期范围、是否过期。

管理员不在个案页面替学生修改记录，也不读取原始日记。若该周期没有 AI 报告，后台显示“该周期暂无已生成报告”，不能自动生成一段假结论。

### 6.2 隐私和权限边界

- 后台接口必须从 `caseId` 服务端解析 `student_user_id`，不接受前端随意传入其他学生 ID。
- 仅管理员、超级管理员和被分配的心理工作人员可访问；学生和无关工作人员返回 403。
- 返回聚合情绪数据、结构化报告和触发依据，不返回 `note_ciphertext`、解密日记、树洞原文或咨询对话原文。
- AI 报告若曾经使用日记授权，只显示“曾使用用户授权内容”标识，不把原文复制到后台。
- 风险触发是支持提醒，不得在页面写成医学诊断。
- 访问个案情绪证据应写入审计日志。

### 6.3 风险规则和触发时机

现阶段保留已经实现的三类“任一满足即可”信号，但必须补充角色过滤，只对学生账号创建个案。

“连续 7 天低于 5”当前使用的是情绪强度字段，和“总体状态分”存在语义混用风险。本轮可以保留它作为毕业设计演示规则，但页面应称为“连续低分预警”，不得宣传为临床标准。正式部署前必须单独确认量表含义，或新增明确的每日状态评分字段后再冻结阈值。

自动建案不应依赖管理员打开列表这一隐藏副作用。推荐在学生提交情绪记录后异步评估该学生，并保留定时扫描作为补偿机制；管理员刷新只读取结果。树洞和 AI 问答高风险信号继续在事件发生时记录。

## 7. 可验收的演示数据方案

新增独立学生演示账号，例如 `demo_risk_student`，不得复用管理员账号。该账号至少包含：

- 最近连续 7 个自然日都有主情绪记录；
- 每日值符合当前“低于 5”演示规则；
- 使用焦虑、难过、疲惫等多种负向情绪，不再全部填充快乐；
- 包含可解释的学习、睡眠、同伴关系等触发标签；
- 只写原始情绪记录，不预写 AI 报告或个案结论；
- 运行风险评估后自动产生一条高风险待处理个案，并显示“连续 7 天情绪记录评分低于 5 分”；
- 重复运行种子保持幂等，不重复生成多个学生或多个自动个案。

保留一个不触发风险的普通学生作为对照组，用于证明系统不是“只要有记录就建案”。现有 365 天账号可继续用于长周期图表测试，但不再承担风险触发验收。

## 8. 数据与接口边界

推荐形成三层唯一来源：

1. `MoodAggregationService`：按统一周期返回数据范围、独立记录数、分布和趋势，是用户页与后台个案页的共同数据源。
2. `MoodAnalysisService`：使用同一数据范围构造 AI 请求，管理分析版本和真实性状态。
3. `RiskEvidenceService`：根据 `caseId` 组合触发原因、聚合数据和已落库报告，不读取原始正文。

后台可以新增类似 `GET /api/cases/:caseId/mood-evidence?period=7d` 的只读接口。响应中明确区分：

- `facts`：数据库计算事实；
- `analysis`：AI 生成内容；
- `riskSignals`：规则命中证据；
- `provenance`：生成和数据版本信息。

风险规则不得直接解析 AI 报告中的自由文本来建案，避免模型输出不稳定地影响安全流程。建案仍由确定性规则和已经结构化记录的高风险事件驱动。

## 9. 实施阶段与原子提交建议

按照项目“小改动单独提交”的要求，实施时建议拆成以下提交，每一步都保持可回退：

1. 统一周期类型和服务端日期范围，修复 3 个月、6 个月数据口径。
2. 统一 `patterns[].evidence` 合同并增加历史字符串兼容。
3. 修复真实 provider 标识和 AI 完成态校验。
4. 重构用户侧周期状态机，始终保留周期选择和合法操作按钮。
5. 合并导航与路由，保留旧地址重定向，删除确认无引用的重复页面。
6. 新增风险个案情绪证据只读接口、权限与审计。
7. 在个案详情接入完整图表、结构化报告和溯源信息。
8. 新增独立风险学生种子、对照数据和自动建案验收。
9. 补充跨周期、AI 失败、权限、隐私和浏览器端到端测试。

每次提交只暂存本任务明确列出的文件，不使用全量 `git add`，不整理当前工作区其他未提交改动。

## 10. 验收标准

### 10.1 用户侧

- 导航中只存在一个“情绪洞察”入口，旧链接能够重定向。
- 先完成 1 个月分析，再选择 3 个月时，3 个月操作区正常出现，不显示错误的 1 个月完成状态。
- 演示账号的 3 个月、6 个月、1 年页面分别明确显示 93、182、365 条或基于验收时数据库实时计算出的对应完整记录数，不被 20 条分页或 1 个月映射截断。
- 图表、数据范围与 AI 报告使用同一周期。
- “发现的模式”按完整依据句子显示，不逐字符、不溢出。
- AI 服务不可用时显示真实失败；数据库中没有成功报告，页面也不得显示“分析完成”。
- 成功报告能够追溯生成时间、报告编号、数据范围和真实模型信息。

### 10.2 风险个案

- 最近连续 7 日满足规则的学生自动进入风险个案，普通对照学生不进入。
- 个案列表显示具体触发原因，详情显示对应周期完整图表和已落库结构化 AI 报告。
- 后台 Network 响应、页面 DOM 和日志中均不出现原始日记正文、树洞原文或咨询对话原文。
- 无权限账号访问个案情绪证据接口返回 403。
- 同一学生重复评估不会产生重复自动个案，但会更新最近命中时间和证据。
- 管理员无需通过“打开列表触发写入”才能看到已经命中的个案。

### 10.3 验证证据

完成不能只以单元测试、HTTP 200 或健康检查判断。最终至少需要：

- 前端组件与状态机测试；
- Node 合同、权限、聚合与风险规则测试；
- FastAPI 合同与 Provider 输出测试；
- MySQL 中分析版本、来源字段和自动个案的只读核查；
- 浏览器实测 1 个月切换 3 个月、长周期完整记录、“发现的模式”排版和后台个案详情；
- AI 服务故障时的失败关闭场景；
- 页面与 Network 的原始正文泄漏检查。

## 11. 不在本轮范围

- 不批量迁移或重写历史情绪记录。
- 不把 AI 报告作为医学诊断或唯一风险判定依据。
- 不向管理员展示原始日记、树洞原文或咨询对话。
- 不在本方案阶段直接修改生产风险阈值；阈值语义需另行评审。
- 不为演示方便直接向数据库写入伪造 AI 报告或预制风险结论。

## 12. 推荐实施顺序

先修复周期与数据合同，再修复页面状态机和入口合并；随后建设后台只读证据接口及页面；最后准备独立风险学生数据并完成真实浏览器、AI、数据库和隐私验收。这样可以确保后台展示建立在已经统一的数据与报告合同上，避免先复制一套仍然错误的用户侧逻辑。
