# 大学生情绪健康管理平台渐进式定向重构设计

## 文档状态

- 状态：已审核并冻结（V4 Final）
- 日期：2026-07-14
- 适用阶段：R0 代码重构与架构稳定、P0/v1.0 核心闭环建设、v1.1 AI 增强
- 关联决策：[ADR-001：采用 MySQL 单数据库与渐进式分层架构](../../architecture/ADR-001.md)

## 1. 背景与结论

现有项目已经具备 Vue 3 前端、Node.js/Express 后端、数据库、情绪记录、心理测评、社区、活动、放松资源和管理后台等功能，不需要整体重写。但项目同时存在 API 响应格式不统一、登录恢复和问卷链路故障、SQLite 与 SQL Server 双分支、Model 职责过重、运行时建表、测试依赖旧数据库状态、AI 调用路径不一致及心理安全边界不足等问题。

本项目采用“渐进式定向重构”，冻结新增功能，先建立可重复的工程基础和测试基线，再逐个领域迁移到 MySQL。任何阶段都不得以架构升级为理由大规模重写 UI、路由或全部 Model。

实施顺序固定为：`代码重构 → 架构稳定 → P0/v1.0 核心业务开发 → v1.1 AI 接入`。当前处于 R0 代码重构阶段，不把未来 P0 功能或 AI 功能混入当前重构切片。

## 2. 目标与非目标

### 2.1 目标

1. 建立可构建、可测试、可启动、可回退的工程基线。
2. 将数据库统一为 MySQL，最终删除 SQLite 与 SQL Server 运行时代码。
3. 统一后端响应、前端解包、错误处理和接口类型。
4. 建立 Controller、Service、心理评估规则层、Repository 的清晰边界。
5. 完成学生、心理工作人员和超级管理员三级角色的轻量 RBAC。
6. 形成“监测与筛查—风险预警—风险个案—人工处理—专业转介—结案审计”闭环。
7. 让心理分析、量表计分、风险分层和 AI 建议具备理论来源、版本记录和明确的非诊断边界。
8. 为毕业论文、答辩和 AI 产品经理作品沉淀可追踪的需求、架构、测试和迭代材料。

### 2.2 非目标

- 不进行整体重写。
- 不引入微服务、消息队列、Kubernetes、Redis 集群、分布式锁或自建大模型。
- 不开发动态角色、用户多角色或可视化权限编辑器。
- 不在 P0 新增或重做社区、活动、课程、放松资源和成就功能。
- 不自行创造心理指标、诊断阈值、风险诊断逻辑或“AI 心理模型”。
- 不承诺商业级高并发，部署目标是毕业设计展示、小规模测试和项目演示。

## 3. 阶段与版本范围

### 3.1 R0：代码重构与架构稳定（当前阶段）

R0 不开发新的 P0 业务功能，目标是治理现有 SQLite、SQL Server 分支和高耦合代码，为后续业务开发建立稳定基础。范围包括：

1. 建立可重复的构建、测试、启动和回退基线。
2. 修复核心链路已有故障与 API 响应契约不一致。
3. 建立 MySQL、Redis、Docker Compose、Migration、Seed 和 Repository 基础设施。
4. 按领域渐进迁移现有核心数据访问，禁止 Service 直接执行 SQL。
5. 停用仍依赖 SQLite 的非核心模块，验证 MySQL 接管后再清理 SQLite 与 SQL Server 残余。

R0 的完成标志是架构边界、数据库迁移机制、核心测试基线和本地运行环境稳定，不以新增产品功能数量作为验收标准。

### 3.2 P0/v1.0：核心业务闭环

1. 用户注册、登录、JWT 鉴权和刷新后的身份恢复。
2. `student`、`counselor`、`super_admin` 三类内置角色及固定权限。
3. 情绪记录、历史查询、趋势和描述性统计。
4. 心理量表管理、作答、经验证规则计分、筛查结果解释和历史记录。
5. 风险识别、风险分层、风险个案、分配、处理、转介、结案和审计。
6. 管理后台中的匿名聚合统计、风险个案处理、用户与权限基础管理、审计日志。

### 3.3 v1.1：AI 增强

在 v1.0 核心闭环和心理安全规则通过验证后，再接入 AI 分析、辅助建议、辅助报告和 Prompt 模板管理。AI 不作为 R0 或 v1.0 的首要开发任务，也不得阻塞毕业设计核心闭环交付。

### 3.4 暂停项

社区、活动、课程、放松资源和成就等现有模块保留代码，但在 R0 和 v1.0 MySQL 运行环境中通过功能开关关闭入口，不允许继续访问 SQLite。它们不作为 v1.0 验收路径，待 P1/P2 完成 MySQL 迁移和测试后再逐个启用。

## 4. 目标架构

```text
Vue 3 + TypeScript
        ↓
Express API / Middleware
        ↓
Controller
        ↓
Service
├── 普通业务
│   ├── 用户与认证
│   ├── 情绪记录与趋势
│   ├── 风险个案处理
│   └── 后台管理
├── 心理评估规则层
│   ├── 量表管理
│   ├── 评分规则
│   ├── 风险分层规则
│   └── 理论依据
└── AI Gateway（v1.1） ─────→ 外部 AI API
        ↓
Repository
        ↓
MySQL + Redis
```

Service 包含普通业务编排和心理评估规则能力；心理评估规则层不是位于 Service 与 Repository 之间的强制流水线。Repository 保持独立并作为唯一数据库访问边界，普通业务、心理评估规则和 v1.1 AI Gateway 均只能通过 Repository 读写 MySQL。AI Gateway 直接调用外部 AI API，MySQL 不主动调用 AI 服务。

## 5. 组件职责

### 5.1 前端

- `request.ts` 统一附加身份信息、判断业务码、处理通用错误并返回业务 `data`。
- `src/api` 按领域提供明确的 TypeScript 输入与返回类型。
- 页面不读取 `response.code`、`response.message` 或 `response.data`。
- 页面负责交互、状态展示和业务数据渲染，不重复实现请求协议。
- P0 暂停模块通过显式功能开关隐藏入口，不通过删除路由或删除代码实现。

### 5.2 Express API 与中间件

- 负责 JWT 鉴权、RBAC、参数校验、限流、统一响应和错误处理。
- 权限判断以后端为唯一可信来源；前端菜单和按钮显隐只用于改善体验。
- 所有隐私数据访问必须经过身份、权限、数据范围和审计检查。

### 5.3 Controller

- 接收并校验请求参数。
- 调用 Service。
- 将结果转换为响应 DTO。
- 不编写核心业务规则，不直接执行 SQL。

### 5.4 Service

- 负责编排领域业务、事务边界和跨模块流程。
- 通过 Repository 访问数据，禁止直接编写 SQL。
- 普通业务和心理评估规则层是 Service 内的两类能力，不把心理评估规则层设计成独立服务或数据库访问中间层。
- 心理测评、风险识别和 v1.1 AI 建议必须复用已批准的心理评估规则，不得在 Controller、页面或 Prompt 中复制计分和分层规则。

### 5.5 心理评估规则层

- 管理已批准量表、评分规则、风险分层规则、建议模板和理论依据。
- 只实现有正式来源且适用于目标人群的规则。
- 量表、计分、风险分层、中文版本、适用人群和授权状态在启用前完成核对。
- 架构阶段只定义量表管理、评分规则、风险分层和理论依据，不预先锁定具体量表。最终量表必须根据论文方向、指导老师要求、适用人群、中文验证研究和使用授权另行确认。
- 统一使用“筛查”“风险提示”“风险分层”等表述，禁止自创心理模型、自动诊断或将筛查结果描述为医学诊断。

### 5.6 Repository

- 是唯一数据库访问边界。
- 使用 `mysql2/promise`，封装查询、事务和行到领域对象的映射。
- 不建立复杂的通用 Repository 基类，不为了复用制造抽象。
- 每个领域独立迁移和测试，避免一次性改写全部 Model。

### 5.7 MySQL 与 Redis

- MySQL 是唯一业务数据源，保存业务数据、风险个案、审计日志，以及 v1.1 启用后的 AI 分析记录。
- 数据库结构只通过版本化 Migration 变更，禁止 Model 运行时建表。
- Seed 生成虚构、可重复、能覆盖核心演示路径的高质量演示数据。
- Redis 用于查询缓存、限流辅助，以及可选的 AI 缓存；Redis 不是业务事实来源。

### 5.8 AI Gateway（v1.1）

- 执行数据最小化和脱敏。
- 选择并记录 Prompt 模板版本。
- 调用外部 AI 模型，并处理超时、失败重试和安全降级。
- 校验结构化输出，拒绝诊断性、自创分数或越过安全边界的内容。
- AI 分析记录包含 `input_summary`、模型版本、Prompt 版本、调用时间、状态和 AI 返回。
- `input_summary` 只保存去标识化、非原文的最小摘要，例如“近 7 天负面情绪表达频率升高”；不保存用户原始隐私文本或可反推出身份的内容。
- 所有 AI 建议必须附带非诊断免责声明。
- 高风险信号不得仅返回普通 AI 建议，必须进入风险预警和人工处理流程。

## 6. API Response Contract

成功响应使用标准 HTTP 状态码，并统一返回：

```json
{
  "code": 0,
  "message": "success",
  "data": {}
}
```

失败响应使用合适的 HTTP `4xx` 或 `5xx` 状态码，响应体 `code` 为非零业务码。HTTP 状态码描述协议层结果，业务码描述具体业务错误，两者不得混用。

迁移期间 `request.ts` 可以暂时兼容旧接口；所有接口迁移完成并通过契约测试后，删除 `code === 200`、无 `code` 响应和页面重复 `.data` 解包逻辑。

## 7. 角色、数据范围与审计

### 7.1 固定角色

- `student`：记录情绪、完成筛查、查看本人结果和辅助建议。
- `counselor`：查看匿名聚合统计，处理分配给自己的风险个案。
- `super_admin`：维护用户、系统配置、内置角色权限、个案分配和审计，不默认查看心理内容正文。

### 7.2 轻量 RBAC

P0 使用 `users`、`roles`、`permissions`、`role_permissions`。三类角色通过 Seed 初始化，一个用户只拥有一个角色。P0 不提供角色新增、删除和权限编辑页面。

### 7.3 最小必要访问

- `counselor` 默认不能浏览全部学生情绪和测评明细。
- 普通管理统计只返回匿名化聚合数据。
- 风险个案详情仅对被分配的 `counselor` 开放。
- 学生授权、紧急介入、个案访问、状态变更和转介操作必须记录审计日志。

## 8. 心理科学性与 AI 安全边界

1. 平台提供日常记录、筛查、风险预警和辅助支持，不提供医学诊断。
2. 筛查阳性只代表需要进一步评估，不直接等同于疾病或高风险诊断。
3. 关键词或文本信号只能触发预警流程，不能单独生成心理诊断。
4. AI 只能基于已批准规则和最小必要上下文生成解释或建议草案。
5. AI 不得修改量表得分、创建心理指标、独立判定风险等级或替代专业人员。
6. 风险个案必须由受训人员处理，并根据实际情况转介专业心理或医疗机构。
7. 所有心理相关规则必须保存来源、版本和适用范围，便于论文引用和后续审查。

以下资料仅用于确定 AI 治理、学生心理健康工作和风险预警后的人工处理原则，不构成具体量表选型结论：

- [WHO：健康人工智能伦理与治理指南](https://www.who.int/publications/i/item/9789240037403)
- [NIMH：ASQ 自杀风险筛查工具与后续人工评估路径](https://www.nimh.nih.gov/research/research-conducted-at-nimh/asq-toolkit-materials)
- [教育部等十七部门：全面加强和改进新时代学生心理健康工作专项行动计划](https://www.gov.cn/zhengce/zhengceku/202305/content_6857361.htm)

## 9. 核心数据流

### 9.1 情绪记录与趋势

```text
student 提交情绪记录
→ API 鉴权与参数校验
→ Mood Service
→ Mood Repository
→ MySQL
→ 生成描述性统计与趋势
→ 返回业务 data
```

### 9.2 心理测评

```text
student 选择已批准量表
→ 加载量表版本与题目
→ 提交完整答案
→ 心理评估规则层执行原始计分规则
→ 保存逐题答案、总分、结果解释和规则版本
→ 展示筛查结果及非诊断提示
```

### 9.3 风险闭环

```text
验证量表或风险识别
→ 风险预警
→ 创建风险个案
→ super_admin 分配 counselor
→ counselor 人工处理
→ 支持或专业转介
→ 结案
→ 全程审计
```

### 9.4 AI 辅助建议（v1.1）

```text
student 主动请求建议
→ 后端鉴权与最小数据读取
→ 心理评估规则层提供已批准规则与建议边界
→ AI Gateway 脱敏并选择 Prompt 模板
→ 调用外部 AI API
→ 超时、降级与输出校验
→ Repository 保存 AI 分析记录
→ 返回附免责声明的辅助建议
```

## 10. 错误处理与降级

- MySQL 不可用：核心写操作失败并返回明确错误，不转写 SQLite。
- Redis 不可用：查询回退到 MySQL，限流采用安全默认行为并记录告警；Redis 故障不得导致数据丢失。
- AI API 超时或失败：返回经过审核的固定安全提示，不伪造 AI 结果。
- AI 输出不符合结构或安全规则：拒绝展示，记录失败状态，并使用安全降级内容。
- 风险信号命中：优先展示求助与人工处理路径，不继续普通建议流程。
- 功能开关关闭：社区、活动和资源入口不可见，后端对应接口默认拒绝新调用，避免隐式访问旧数据库。

## 11. 数据库迁移策略

1. 保留旧 SQLite 文件的离线备份，但不迁移其中的脏数据。
2. 先确认 SQL Server 没有实际运行依赖，再以独立切片删除 SQL Server 分支、配置、依赖和文档。
3. 使用 Docker Compose 启动本地 MySQL 与 Redis。
4. 增加 MySQL 连接、配置校验和健康检查，不立即切换业务流量。
5. 建立最小 Migration 执行器和版本表。
6. 按“用户与认证→RBAC→情绪→测评→风险个案→后台”的顺序迁移 v1.0 核心领域。
7. 每个领域完成 Migration、Seed、Repository、接口测试和人工验证后，再进入下一个领域。
8. 所有 P0 领域通过后，将默认数据库切换为 MySQL。
9. 验证活动运行路径不存在 SQLite 访问后，以独立切片删除 P0 核心模块中的 SQLite 代码、配置和脚本。
10. 社区、活动、资源和成就保持关闭；其未迁移源码可以保留 SQLite 遗留实现，但不得被应用入口导入或执行，待 P1/P2 迁移 MySQL 后再删除对应 SQLite 实现并启用。
11. v1.0 核心闭环稳定后，再为 v1.1 增加 AI 分析记录 Migration 和 Repository，不提前混入 R0 数据库迁移。

迁移过程中允许 SQLite 与 MySQL 暂时共存以便回退和对照，但单次业务运行不得跨库组合数据，也不建设长期双数据库兼容层。P0/v1.0 的退出门槛是活动运行路径零 SQLite；全仓 SQLite 遗留源码的最终清除随 P1/P2 非核心模块迁移完成。

## 12. Docker 与部署

### 12.1 本地开发

```text
Docker Compose：MySQL + Redis
宿主机：Vite + Node.js/Express 热更新
```

### 12.2 阿里云 2 核 2G

```text
Docker Compose：Nginx + Node.js API + MySQL + Redis
外部服务：AI API
```

部署配置必须包含健康检查、持久化 Volume、环境变量、资源限制、自动重启策略和 MySQL 备份恢复脚本。服务器不运行自建大模型。

### 12.3 2 核 2G 初始资源上限

以下是毕业设计演示环境的初始保护值，最终值需根据部署冒烟和小规模压测结果调整：

| 组件 | 初始限制 | 说明 |
|---|---:|---|
| MySQL | `max_connections=30` | Node.js 连接池初始上限为 10，避免连接数耗尽内存；建议 `innodb_buffer_pool_size=256M` |
| Redis | `maxmemory=128mb` | 使用 `allkeys-lru`；仅保存可丢弃缓存和限流状态，不保存业务事实 |
| Node.js API | 单进程、容器内存上限 `512M` | 设置 `NODE_OPTIONS=--max-old-space-size=384`，不启用 cluster 或 PM2 多实例 |

Nginx、操作系统和 Docker 运行时必须保留必要内存余量。若出现持续内存压力，优先缩减缓存和连接池，而不是增加并行进程。

## 13. 增量实施规则

- 一次只改变一个逻辑目标。
- 数据库迁移、接口契约修改、页面调整和功能开发分开提交。
- 每个切片完成后运行相关测试、类型检查、构建和人工验证。
- 每个 Migration 必须有明确回退方式；破坏性删除独立执行。
- 不顺手清理无关文件，不在功能提交中混入大范围格式化。
- 新架构只在正在迁移的领域中逐步落地，不先建立空泛抽象。

## 14. 测试与完成标准

### 14.1 测试层级

- 单元测试：计分规则、风险分层规则、权限判断、错误映射。
- Repository 集成测试：使用独立 MySQL 测试库验证查询、事务和约束。
- API 契约测试：验证 HTTP 状态、`code`、`message` 和 `data`。
- v1.0 端到端测试：登录恢复、情绪记录与趋势、量表提交、风险个案和权限隔离。
- v1.1 AI 测试：脱敏、`input_summary`、Prompt 版本、超时降级、输出校验和免责声明。
- 部署冒烟：干净环境 Migration、Seed、启动、健康检查和核心页面访问。

### 14.2 每个切片的完成标准

1. 任务验收条件全部满足。
2. 相关自动化测试通过。
3. 前后端构建和类型检查通过。
4. 核心人工验证通过。
5. 没有引入新的 SQLite 或 SQL Server 依赖。
6. 文档、Migration 和 Seed 与代码一致。
7. 改动可独立回退。

## 15. 风险与控制

| 风险 | 影响 | 控制方式 |
|---|---|---|
| MySQL 迁移范围失控 | 延期、回归困难 | 按领域切片，P0 暂停非核心模块 |
| 旧接口兼容长期保留 | 协议继续混乱 | 契约测试通过后设置明确删除任务 |
| 心理规则缺少可靠依据 | 论文与安全风险 | 启用前核对来源、版本、人群和授权 |
| AI 输出误导用户 | 心理安全风险 | 输出校验、免责声明、人工流程和安全降级 |
| counselor 越权查看 | 隐私风险 | 个案分配、数据范围校验和审计日志 |
| 2 核 2G 资源不足 | 部署不稳定 | 外部 AI、容器资源限制、Redis 可选缓存、性能测试 |
| 现有测试依赖脏数据 | 无法重复验证 | 独立 MySQL 测试库、Migration 和确定性 Seed |

## 16. 冻结决策

以下决策已经批准，不在后续重构计划或 P0 PRD 阶段重复讨论：

1. 采用渐进式定向重构，不整体重写。
2. 最终只维护 MySQL，使用 `mysql2/promise + Repository + 版本化 SQL Migration`。
3. 本地和阿里云均使用 Docker Compose 管理 MySQL 与 Redis。
4. 后端统一包装 `{ code, message, data }`，成功业务码为 `0`；前端统一解包。
5. 采用 `student`、`counselor`、`super_admin` 固定三级轻量 RBAC。
6. counselor 只访问匿名统计和被分配的风险个案。
7. 心理评估和 AI 坚持循证、非诊断和人工负责原则。
8. P0 暂停社区、活动、资源和成就模块，P1/P2 迁移后再启用。
9. 架构 V4 Final 冻结，不继续增加架构复杂度。
10. 当前先完成 R0 代码重构与架构稳定，P0/v1.0 再开发核心闭环，v1.1 才接入 AI 增强。
11. AI 分析记录保存最小化的 `input_summary`，不保存原始敏感文本。
