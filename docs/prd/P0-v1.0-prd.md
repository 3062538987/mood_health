# P0/v1.0 产品需求文档

## 1. 文档状态

- 状态：草稿，待审核
- 日期：2026-07-16
- 版本：v1.0-draft-1
- 上游：R0 架构稳定验收（Checkpoint F 已批准）
- 架构基座：MySQL 8.4 + Repository 模式 + 统一 API 契约

## 2. 产品目标

在 R0 建立的稳定架构基座上，完成大学生情绪健康管理平台的核心业务闭环，使其具备面向真实用户的**最小可用能力**。

R0 已建立：用户认证、RBAC 权限、情绪记录、通用测评存储、管理聚合、审计日志。v1.0 在此基础上增加：

1. **风险个案管理**：从筛查到结案的完整工作流。
2. **心理量表就绪**：确认并录入至少一套经批准的心理量表，具备完整的计分与风险分层。
3. **数据治理**：明确的数据删除、保留期限和管理员操作权限。

## 3. 范围与非范围

### 3.1 v1.0 纳入范围

| 领域 | 内容 |

## 4. 功能需求

### 4.1 风险个案管理

#### 4.1.1 个案创建

- 触发条件：学生提交心理量表后，筛查结果达到预设风险分层阈值。
- 创建方式：系统自动创建（量表提交触发）+ 咨询师手动创建。
- 个案状态：`open`（待处理）、`assigned`（已分配）、`in_progress`（干预中）、`referred`（已转介）、`closed`（已结案）。

#### 4.1.2 咨询师分配

- super_admin 或具有分配权限的 counselor 可将个案分配给指定咨询师。
- 分配记录写入审计日志。
- 一个个案同时只分配给一位咨询师（R0 简化模型）。

#### 4.1.3 干预记录

- 咨询师可在个案下记录干预措施、沟通摘要和后续计划。
- 干预记录为纯文本，不包含 AI 生成内容。
- 每条干预记录附带时间戳和操作者信息。

#### 4.1.4 转介

- 咨询师可将个案标记为"需转介"，并填写转介原因和外部机构信息。
- 转介后个案状态变为 `referred`，不再接受本平台干预操作。
- 转介记录可查看但不可修改。

#### 4.1.5 结案

- 咨询师可结案并填写结案摘要。
- 结案后状态变为 `closed`，个案数据保留但不可再编辑。
- 结案条件由业务规则定义，不在数据库层强制约束。

#### 4.1.6 权限矩阵

| 权限编码 | student | counselor | super_admin |
|---|:---:|:---:|:---:|
| `case.read_assigned` | | 仅分配给自己 | 全部 |
| `case.create` | | ✓ | ✓ |
| `case.assign` | | | ✓ |
| `case.intervene` | | 仅分配给自己 | |
| `case.refer` | | 仅分配给自己 | ✓ |
| `case.close` | | 仅分配给自己 | ✓ |
| `case.read_own` | ✓ | | |

### 4.2 心理量表就绪

#### 4.2.1 量表确认

- 确认至少一套经批准的心理量表（如 PHQ-9、GAD-7 或 SDS/SAS 的正式授权版本）。
- 量表需具备：正式来源引用、使用授权说明、计分规则、风险分层阈值。
- 未经确认的量表不得进入 `active` 状态。

#### 4.2.2 录入内容

- 量表元数据（名称、适用人群、理论依据、来源引用、授权说明）。
- 题目（题号、文本、题型、选项及原始值、是否反向计分）。
- 计分规则 JSON（`scoring_rule_json`）。
- 风险分层 JSON（`risk_stratification_json`）。
- 建议模板 JSON（`suggestion_template_json`）。

#### 4.2.3 前端流程

- 学生：量表列表 → 答题 → 提交 → 查看筛查结果（含非诊断提示）。
- 咨询师：查看已分配学生的测评历史与筛查结果。
- 筛查结果文案统一使用"风险提示"、"建议进一步评估"，不出现"诊断"、"确诊"。

#### 4.2.4 旧代码处置

- 现有 `questionnaireController.ts` 中写死的 SDS/SAS 计分规则**必须删除**，改为调用 `assessment_instrument_versions.scoring_rule_json`。
- 旧 `questionnaires`、`questions` 表（SQLite）不再使用，MySQL 中对应 `assessment_instruments` 系列表作为唯一数据源。

### 4.3 数据治理

#### 4.3.1 账号停用

- super_admin 可将用户状态设为 `disabled`。
- 停用账号不可登录，不接收新 token。
- 停用账号的已有数据保留，不计入匿名聚合统计。

#### 4.3.2 物理删除

- 仅 super_admin 可执行物理删除。
- 删除前必须二次确认，并写入审计日志。
- 物理删除级联删除：用户 → 情绪记录 → 测评记录 → 个案记录。
- 审计日志中 `actor_user_id` 在用户被删除后设为 NULL，保留角色快照和操作摘要。

#### 4.3.3 数据保留期限

- 默认保留期限：账号停用后 90 天自动物理删除（可配置）。
- 未结案个案在结案后保留 180 天（可配置）。
- 保留期限到期前 7 天系统发出提醒。
- 具体数值由部署时环境变量配置，不硬编码。

#### 4.3.4 管理员操作权限

- 物理删除、角色分配、量表启用/停用均需 super_admin 权限。
- 所有管理操作写入审计日志。
- counselor 不具备用户管理或数据删除权限。

### 4.4 旧表处置

| 表名 | 处置 |
|---|---|
| `incident_fix_list` | 逻辑由风险个案模块替代，不迁移到 MySQL，物理删除 |
| `feedback_close_list` | 逻辑由个案结案替代，不迁移到 MySQL，物理删除 |

## 5. 数据模型新增

### 5.1 `cases`（风险个案）

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | `INT UNSIGNED` | PK, AUTO_INCREMENT | 个案 ID |
| `student_user_id` | `INT UNSIGNED` | NOT NULL, FK→`users.id` | 学生 |
| `assigned_counselor_id` | `INT UNSIGNED` | NULL, FK→`users.id` | 分配咨询师 |
| `source_session_id` | `INT UNSIGNED` | NULL, FK→`assessment_sessions.id` | 触发量表批次 |
| `status` | `VARCHAR(16)` | NOT NULL, DEFAULT `open`, CHECK | `open`、`assigned`、`in_progress`、`referred`、`closed` |
| `risk_level` | `VARCHAR(32)` | NULL | 触发时的风险分层快照 |
| `summary` | `TEXT` | NULL | 个案摘要（脱敏） |
| `created_at` | `DATETIME(3)` | NOT NULL | 创建时间 |
| `updated_at` | `DATETIME(3)` | NOT NULL | 更新时间 |

索引：`(student_user_id, status)`、`(assigned_counselor_id, status)`、`status`。

### 5.2 `case_interventions`（干预记录）

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | `INT UNSIGNED` | PK, AUTO_INCREMENT | 记录 ID |
| `case_id` | `INT UNSIGNED` | NOT NULL, FK→`cases.id` | 所属个案 |
| `counselor_user_id` | `INT UNSIGNED` | NOT NULL, FK→`users.id` | 操作咨询师 |
| `intervention_type` | `VARCHAR(32)` | NOT NULL | 类型：`note`、`interview`、`referral`、`closure` |
| `content` | `TEXT` | NOT NULL | 干预内容（脱敏） |
| `referral_target` | `VARCHAR(255)` | NULL | 转介外部机构 |
| `referral_reason` | `TEXT` | NULL | 转介原因 |
| `closure_summary` | `TEXT` | NULL | 结案摘要 |
| `created_at` | `DATETIME(3)` | NOT NULL | 记录时间 |

### 5.3 新增权限

| 权限编码 | 说明 |
|---|---|
| `case.read_assigned` | 读取已分配个案 |
| `case.read_own` | 学生读取本人个案 |
| `case.create` | 创建个案 |
| `case.assign` | 分配个案 |
| `case.intervene` | 记录干预 |
| `case.refer` | 转介 |
| `case.close` | 结案 |
| `user.delete` | 物理删除用户 |

## 6. 非功能需求

### 6.1 资源约束

沿用 R0 的 2 核 2G 配置：

| 配置 | 值 |
|---|---|
| MySQL `max_connections` | 30 |
| Node.js MySQL Pool `connectionLimit` | 10 |
| MySQL `innodb_buffer_pool_size` | 256M |
| Redis `maxmemory` | 128MB |
| Node.js API | 单进程，容器 512MB |

### 6.2 安全

- 个案内容、干预记录为敏感数据，仅已分配咨询师和 super_admin 可读。
- 转介信息中的外部机构名称不包含学生个人标识。
- 审计日志不记录个案正文内容，只记录操作类型和对象 ID。

### 6.3 可用性

- 量表提交后立即显示筛查结果，不依赖异步队列。
- 咨询师可查看已分配学生的测评历史和情绪趋势。
- 个案列表支持按状态筛选和按创建时间排序。

## 7. 验收标准

### 7.1 风险个案

- [ ] 学生提交量表后，达到阈值时自动创建个案。
- [ ] 咨询师可手动创建个案。
- [ ] super_admin 可分配个案给咨询师。
- [ ] 咨询师可记录干预、转介和结案。
- [ ] 学生可查看本人个案状态。
- [ ] 权限矩阵中所有路径通过自动化测试。

### 7.2 心理量表

- [ ] 至少一套量表数据完整录入 MySQL（元数据、题目、规则、分层）。
- [ ] 前端可完成量表提交并查看筛查结果。
- [ ] 旧 SDS/SAS 硬编码计分规则已删除，改为调用 MySQL 中存储的规则。
- [ ] 筛查结果文案不含"诊断"、"确诊"等未授权表述。

### 7.3 数据治理

- [ ] 账号停用后不可登录。
- [ ] 物理删除级联清理用户数据，审计日志保留操作记录。
- [ ] 数据保留期限可配置，到期前有提醒。
- [ ] 所有管理操作有审计日志。

### 7.4 构建与测试

- [ ] `npm run build:all` 退出 0。
- [ ] `npm run test:all` 全部通过（新增个案、量表、数据治理相关测试）。
- [ ] 新增 Migration 通过 `up → down → up` 测试。
- [ ] 新增 Seed 可重复执行且不产生重复数据。

## 8. 实施顺序

```
量表确认与录入
    ↓
风险个案表 Migration + Repository
    ↓
个案 Service + Controller
    ↓
权限扩充 Migration + Seed
    ↓
数据治理实现
    ↓
旧代码清理（硬编码规则、旧表）
    ↓
v1.0 验收
```

## 9. 风险与控制

| 风险 | 影响 | 控制方式 |
|---|---|---|
| 量表确认周期长 | 阻塞风险个案联动 | 先录入一套技术测试量表，正式量表确认后替换 |
| 个案权限过于简化 | 不符合真实咨询场景 | R0 阶段只做单角色单分配，P2 可扩展为多咨询师协作 |
| 数据删除不可逆 | 误删数据无法恢复 | 物理删除前二次确认 + 审计日志 + 软删除宽限期 |
| 旧规则与新规则并存 | 学生看到不一致结果 | 严格删除旧 Controller 硬编码，只保留 MySQL 规则 |
