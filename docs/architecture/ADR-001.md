# ADR-001：采用 MySQL 单数据库与渐进式分层架构

## 状态

Accepted

## 日期

2026-07-14

## 背景

项目当前能够运行，但同时维护 SQLite 和 SQL Server 分支，数据库初始化与建表逻辑分散在配置、脚本和 Model 中。前后端响应结构也不统一，测试依赖旧数据库状态。若在此基础上直接新增 P0 或 AI 功能，会继续扩大维护成本和论文一致性风险。

项目的最高目标是完成计算机专业毕业设计，其次是提高工程质量，并适度沉淀 AI 产品经理作品。目标部署环境为阿里云轻量服务器 2 核 2G，不需要商业级分布式架构。

## 决策

1. 实施顺序固定为“R0 代码重构与架构稳定 → P0/v1.0 核心业务闭环 → v1.1 AI 增强”。当前不直接开发 P0 或 AI 功能。
2. 最终只维护 MySQL，不建设长期双数据库兼容。
3. 保留旧 SQLite 离线备份，但不迁移旧脏数据；MySQL 使用全新 Schema 和高质量 Seed。
4. SQL Server 在确认无运行依赖后删除；MySQL 完成 v1.0 核心领域接管后，活动运行路径必须零 SQLite。被功能开关停用的非核心模块可以暂存 SQLite 遗留实现，待 P1/P2 迁移后最终删除。
5. 数据访问采用 `mysql2/promise + Repository + 版本化 SQL Migration`，不引入 ORM。
6. 后端逐步形成 Route/Middleware → Controller → Service 与 Repository 分层。Service 包含普通业务和心理评估规则能力，Repository 独立作为唯一数据库访问边界。
7. 心理评估规则层只承载量表管理、评分规则、风险分层和理论依据，不预先确定具体量表，不提供自动诊断。
8. 使用 Docker Compose 管理本地与阿里云的 MySQL、Redis；生产环境同时管理 Nginx 与 Node.js API。
9. 采用渐进式迁移，每个领域独立完成 Migration、Seed、Repository、测试和验证。
10. P0/v1.0 暂停社区、活动、资源和成就入口，不允许它们继续访问 SQLite；P1/P2 迁移 MySQL 后再启用。
11. v1.1 再接入 AI 分析、建议、报告和 Prompt 管理。AI 分析记录保存去标识化的 `input_summary`，不保存原始敏感文本。

## 同时确定的接口与权限约束

- 后端统一返回 `{ code, message, data }`，成功业务码为 `0`，HTTP 状态码按标准语义使用。
- `request.ts` 统一解包，页面只处理业务数据。
- 使用 `student`、`counselor`、`super_admin` 三类内置角色的轻量 RBAC。
- counselor 默认只能查看匿名聚合统计和分配给自己的风险个案。
- 心理筛查、风险提示和风险分层必须基于可追溯依据，禁止自创心理模型或自动诊断。
- AI 仅提供辅助能力，不替代专业评估、诊断或风险个案人工处理。

## 部署资源约束

阿里云 2 核 2G 环境采用以下初始上限，后续根据部署冒烟和小规模压测校准：

- MySQL：`max_connections=30`，Node.js 连接池初始上限 10，建议 `innodb_buffer_pool_size=256M`。
- Redis：`maxmemory=128mb`，`maxmemory-policy=allkeys-lru`，不保存业务事实。
- Node.js API：单进程，容器内存上限 `512M`，`NODE_OPTIONS=--max-old-space-size=384`，不启用多实例。

## 备选方案

### 继续使用 SQLite

- 优点：改动最少，部署简单。
- 缺点：不符合项目希望展示的 MySQL 工程实践，现有运行数据与迁移方式混乱。
- 结论：拒绝。

### 继续维护 SQLite 与 SQL Server

- 优点：保留现有兼容能力。
- 缺点：需要双份 SQL、测试、迁移和故障处理，明显超出毕业设计规模。
- 结论：拒绝。

### 使用 Prisma 或其他 ORM

- 优点：类型安全和迁移工具完整。
- 缺点：需要大范围改写现有 Model，容易把数据库迁移升级为整体后端重写。
- 结论：R0 拒绝，采用轻量 Repository。

### 建立新后端并行重写

- 优点：最终代码表面更整洁。
- 缺点：范围大、回归风险高，容易遗漏现有业务，不符合渐进式要求。
- 结论：拒绝。

## 后果

### 正面后果

- 数据库和迁移方式只有一个事实来源。
- 先治理工程基础，避免新功能继续建立在不稳定架构之上。
- MySQL、Redis、Docker、Repository 和测试材料能够支持论文及工程化展示。
- 每个迁移切片可独立测试和回退。
- AI 与心理安全能力建立在稳定的业务数据和权限边界之上。

### 负面后果

- R0 期间暂停新增业务功能，短期看不到明显的功能增长。
- 社区、活动和资源模块在 v1.0 MySQL 环境暂时不可用。
- 需要维护一次受控的 SQLite→MySQL 过渡期，但不得演变为长期兼容层。
- 团队需要自行维护 SQL Migration、Repository 类型和回退验证。

## 实施约束

- 不在一个提交中同时完成数据库迁移、接口改造、UI 重构和新功能。
- MySQL 未验证通过前不删除 SQLite 回退能力。
- v1.0 退出时不得有活动运行路径访问 SQLite；保留的非核心遗留实现不得被应用入口导入或执行。
- 破坏性删除必须独立提交，并在全仓确认零引用后执行。
- Service 禁止直接执行 SQL，Repository 是唯一数据库访问边界。
- Redis 不作为业务事实来源。
- v1.1 之前不接入正式 AI 调用；外部 AI API 只能由 AI Gateway 调用。
- R0 必须先形成代码重构计划和数据库迁移方案，经批准后再执行。
