# AI Development SOP V3.0（精简版）

> 适用：AI辅助开发 / Web项目 / 毕业设计

## 1. 目标
目标不是“代码能跑”，而是“功能真实可用”。任何修改都必须经过开发、测试、审查后才能交付。

## 2. 标准流程
需求分析 → 阅读代码 → 评估影响范围 → 修改代码 → Build → Lint → Type Check → 单元测试 → 接口测试 → Playwright E2E → 浏览器 Console 与 Network 检查 → 后端日志检查 → 人工验收 → 输出测试报告。

任何一步失败，停止交付，修复后重新执行完整流程。

## 3. Quality Gate
### Build
- 项目能够成功构建。
- 不允许 Build Error。

### Lint
- 无 Error。
- Warning 需说明原因。

### Type Check
- TypeScript 无类型错误。

### 单元测试
- 核心业务全部通过。
- 不允许跳过关键测试。

### 接口测试
验证成功、失败、权限不足、参数为空、异常数据、超时等情况。

### E2E 测试
使用 Playwright 模拟真实用户：
- 登录
- 新增
- 编辑
- 删除
- 上传
- 下载
- AI 功能
- 退出登录

禁止只使用 Mock 数据。

### 浏览器检查
确认：
- Console 无 Error
- Network 无 4xx/5xx
- 页面无白屏
- 无未处理 Promise

### 后端检查
确认：
- 无异常日志
- 数据库正常
- Redis / AI 服务正常（如使用）

## 4. Bug 修复规范
1. 定位根因，不猜测。
2. 修复代码。
3. 从 Build 开始重新跑完整流程。
4. 输出修复说明。

禁止“修完不测”。

## 5. AI Code Review
AI 不仅要开发，还要 Review：
- 是否影响其他模块？
- 是否有重复代码？
- 是否有安全风险？
- 是否有性能问题？
- 是否符合项目规范？

Review 未通过，不得交付。

## 6. 测试覆盖建议
P0（必须）：登录、首页、核心业务、数据库写入、AI 功能。
P1（建议）：搜索、筛选、分页、权限、异常流程。
P2（可选）：边界场景、性能、兼容性。

## 7. 交付标准
仅当以下全部满足时，才能声明“开发完成”：
- Build 成功
- Lint 通过
- Type Check 通过
- 单元测试通过
- 接口测试通过
- Playwright 通过
- Console 无 Error
- Network 正常
- 后端日志正常
- 人工验收通过

## 8. 固定 AI Prompt

```text
你是一名资深全栈工程师、测试工程师和 Code Reviewer。

你的目标不是修改代码，而是交付可用的软件。

每次修改后，必须严格执行以下流程：

1. 阅读代码并分析影响范围。
2. 完成代码修改。
3. Build。
4. Lint。
5. Type Check。
6. 运行单元测试。
7. 运行接口测试。
8. 使用 Playwright 执行真实 E2E 测试，不允许仅使用 Mock。
9. 检查浏览器 Console、Network。
10. 检查后端日志。
11. 分析是否影响其他模块，并完成 Code Review。
12. 如任一步失败，停止交付，修复后重新执行完整流程。
13. 最终输出：
   - 修改内容
   - 影响范围
   - 测试结果
   - 风险说明
   - 是否达到交付标准

如果任何质量门未通过，禁止输出“开发完成”。
```

## 9. 一句话原则
**开发不是结束，测试通过才不是结束；真实业务流程验证通过，才允许交付。**
