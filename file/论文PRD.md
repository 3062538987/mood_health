# 二、代码架构分析

## 前端架构

前端目录按 `api`、`components`、`composables`、`stores`、`utils`、`views` 划分，整体合理。

主要问题是API数据契约不统一：

- 请求拦截器已经自动返回业务数据：`D:\桌面\Code\大学生情绪健康\mood-health-web\src\utils\request.ts:108`
- 用户状态恢复仍按旧格式读取 `response.data.user`：`D:\桌面\Code\大学生情绪健康\mood-health-web\src\stores\userStore.ts:82`
- 问卷页面同样重复读取 `.data`：`D:\桌面\Code\大学生情绪健康\mood-health-web\src\views\improve\Questionnaire.vue:88`
- 问卷列表也存在相同问题：`D:\桌面\Code\大学生情绪健康\mood-health-web\src\views\improve\QuestionnaireList.vue:53`

这会导致页面刷新后身份丢失、问卷数据取不到等实际故障。

部分页面体积已经过大：

- `GroupActivity.vue` 约1492行。
- `MoodArchive.vue` 约1304行。
- `MoodRecord.vue` 约1071行。
- `BreathingGuide.vue` 约996行。

应逐步拆分为页面容器、业务组件、状态组合函数和图表组件，但不需要一次性全部重写。

## 后端架构

后端具备标准的：

- 路由层。
- Controller层。
- Model层。
- 认证与权限中间件。
- 数据库、日志、Redis等配置层。

整体方向正确，但Model层承担了过多职责：

- SQL拼接。
- 表结构创建。
- 数据库兼容。
- 业务计算。
- 数据格式转换。

例如情绪模型已经超过1500行，AI模型超过1600行。后续继续增加逻辑会显著提高维护成本。

## API设计

目前存在三种响应风格：

1. `{ code, message, data }`
2. 直接返回数组或对象
3. `{ error }`

例如课程接口直接返回数据：  
`D:\桌面\Code\大学生情绪健康\mood-health-web\mood_health_server\src\controllers\courseController.ts:20`

而认证、情绪和问卷多数返回标准包装结构。前端请求封装为了同时兼容两种形式进行了自动解包，最终导致业务页面理解不一致。

建议统一为：

```text
成功：{ code: 0, message: "success", data: ... }
失败：{ code: 非0, message: "...", details?: ... }
```

并明确约定前端API层返回“包装对象”还是“data”，只能选择一种。

## 数据库设计

数据库实体覆盖较完整：

- 用户、情绪记录、情绪类型、标签。
- 问卷、问题、测评结果和答案。
- 树洞帖子、评论、点赞。
- 活动和参与关系。
- 课程、放松资源和后台日志。

外键、索引、SQLite WAL等基础设计合理。

主要问题：

- SQLite和SQL Server兼容逻辑散布在大量Model中。
- 存在大量 `isSqliteClient` 分支，数据库耦合严重。
- 部分业务表由Model运行时创建，而不是统一迁移。
- 没有明确、唯一、可追踪的数据库版本迁移体系。
- 情绪标签同时存在文本字段和关联表，形成双数据源。
- 问卷提交生成了测评结果，但未看到完整保存每道题答案的调用，和 `user_answers` 表设计不完全一致。

对于毕业设计，建议选择 **SQLite作为唯一演示数据库**，暂时冻结SQL Server扩展，而不是继续维护两套实现。

## 模块耦合

主要耦合点：

- 页面直接理解后端响应包装。
- Model同时负责数据库兼容、建表和业务逻辑。
- 前端权限常量与后端权限常量各自维护。
- AI存在前端本地规则、Node代理、Python服务三套路径。
- 问卷、Survey等相近功能存在重复实现迹象。

整体不是“循环依赖式失控”，但已经出现明显的职责交叉。

# 五、明确建议

## A. 是否需要重构

**需要，但不需要整体重写。**

应进行一次以稳定性、接口契约、数据库迁移和心理安全为中心的定向重构。

## B. 重构范围

建议严格控制在四个范围：

1. **核心链路稳定化**：登录、刷新恢复、情绪记录、问卷、报告。
2. **技术架构收敛**：统一响应结构、SQLite单数据库、统一迁移。
3. **安全整改**：危机识别、HTML清洗、敏感数据库清理。
4. **测试恢复**：干净环境可运行，核心流程全部通过。

暂时不要重写UI、路由系统或所有Model。

## C. 下一步应该开发什么

P0完成后，优先开发“毕业设计核心闭环”，而不是继续增加小游戏或放松资源：

```text
用户登录
→ 情绪记录
→ 情绪趋势分析
→ 心理问卷
→ 个性化建议
→ 风险提示与转介
→ 管理端统计和审核
```

这个闭环最有利于论文、答辩和AI产品经理作品展示。

## D. 推荐开发路线

### 阶段1：稳定化，约3～5天

- 修复响应契约。
- 修复启动脚本。
- 修复测试数据初始化。
- 修复问卷保存。
- 清理数据库和虚拟环境追踪。
- 确保构建、测试和启动全部通过。

### 阶段2：毕业设计P0，约1周

- 打通核心闭环。
- 完成学生、管理员两类完整演示流程。
- 接入危机识别和安全降级。
- 准备固定演示数据。

### 阶段3：产品化P1，约1～2周

- 统一数据库迁移。
- 完善权限和操作日志。

### 阶段4：AI展示P2，约1～2周
